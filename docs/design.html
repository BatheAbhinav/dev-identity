Developer Identity Graph

A single-user backend service that turns a developer's GitHub activity into a queryable, visual graph — repos, languages, collaborators, and organizations as nodes; ownership, authorship, and collaboration as weighted edges.

Stack Java 21 · Spring Boot 4 · H2 · D3 v7 Status Implemented & verified end-to-end Scale target one developer's footprint (10²–10³ nodes)
Overview Architecture Data model Ingestion API Frontend Decisions Security Operations Future work

1Overview

The system answers questions a résumé can't: what do I actually build, in what languages, and with whom? It ingests a GitHub account on demand, stores the result as a graph in two relational tables, and serves both a JSON API and a self-hosted visualization page.

Goals

  • One-command run: ./mvnw spring-boot:run, zero external services.
  • Work without credentials (public data), get strictly better with a token (private + org repos, 5000 req/hr).
  • Honest aggregates — language share weighted by bytes of code, collaboration weighted by shared commits.
  • Exportable output: a self-contained SVG suitable for a GitHub profile README.

Non-goals (v1)

  • Multi-tenant or hosted operation — this is a personal, localhost-first tool.
  • Live updates via webhooks (requires a public endpoint; polling is sufficient).
  • A dedicated graph database — the dataset is thousands of rows, not millions.

2Architecture

Three layers inside one Spring Boot process, plus a static frontend served from the same origin (which eliminates CORS entirely). The GitHub API is the only external dependency.

3Data model

Any graph fits in two tables: nodes and edges. Typing lives in enum columns rather than schema, so adding a node or edge kind is a code change, not a migration.

●USER ■REPO ◆LANGUAGE ▲ORGANIZATION

The four node types, with the shape + color encoding used everywhere in the UI. Collaborators are not a separate type — a collaborator is a USER, so the same person is always one node.

erDiagram
  NODES {
    bigint id PK
    varchar type "USER | REPO | LANGUAGE | ORGANIZATION"
    varchar external_key UK "e.g. repo:octocat/hello-world"
    varchar label
  }
  EDGES {
    bigint id PK
    bigint source_id FK
    bigint target_id FK
    varchar type "OWNS | WRITTEN_IN | ..."
    double weight
  }
  NODES ||--o{ EDGES : "source / target"

external_key is the stable natural key from GitHub (user:octocat, lang:Java), unique-constrained so re-ingestion converges instead of duplicating. Edges are unique per (source, target, type).

Edge semantics

Every edge carries a weight; its meaning is defined per type. This is the doc's most load-bearing table — the weight column is what makes aggregation honest.

EdgeDirectionWeightSource of truth
OWNSuser → repo1.0 (binary)repo listing, owner login match
WRITTEN_INrepo → languagebytes of code/repos/{o}/{r}/languages
COLLABORATES_WITHuser → userΣ min(my commits, theirs) per shared repo/repos/{o}/{r}/contributors
CONTRIBUTED_TOuser → repo not owned1.0, or push/PR event countrepo listing · public events (~90 days)
MEMBER_OFuser → organization1.0 (binary)/users/{u}/orgs

Bytes, not fractions. WRITTEN_IN stores absolute bytes so shares can be aggregated across repos — a 2 MB Python repo outweighs a 10-line HTML one. Percentages (per repo, or across the whole account) are derived at read time. The collaboration weight is deliberately a proxy: true shared-commit analysis would require paging full commit history and isn't worth the API budget at this scale.

4Ingestion pipeline

Ingestion is a full rebuild inside a single transaction, triggered by POST /refresh and executed on a background thread. The steps below are a real sequence — order matters, because credentials are validated and the bulk lists fetched before anything is deleted.

  participant I as IngestionService
  participant GH as GitHub API
  participant DB as H2

  B->>C: POST /refresh {username?, token?}
  C->>C: resolve credentials (fail fast → 400)
  C-->>B: 202 Accepted
  loop poll every 1.5 s
    B->>C: GET /status
  end
  C->>I: refresh(username, token)  [async]
  I->>GH: GET /user or /users/{u} · list repos (paginated)
  I->>DB: BEGIN · delete edges, nodes
  loop each repo
    I->>GH: languages · contributors
    I->>DB: upsert nodes + edges
  end
  I->>GH: orgs · public events
  I->>DB: COMMIT (or ROLLBACK on failure)
  B->>C: GET /graph (fresh data)

Credential resolution

Explicit request values win; GITHUB_TOKEN / GITHUB_USERNAME env vars are the fallback. The resolved pair selects one of four modes:

ProvidedModeRepos visibleRate limit
username onlypublicpublic, owned only60 / hr
token onlyown graphprivate + org + collaborator5000 / hr
both, username = token's loginown graphprivate + org + collaborator5000 / hr
both, someone elsepublic, authenticatedtheir public, owned only5000 / hr
neither—rejected with 400 before any work starts

The "username = token's login" comparison needs one /user call, so it resolves lazily — controller-side validation stays network-free. This rule exists because of a real bug: the UI remembers the username, so users naturally fill both fields, and the naive rule ("username present → public mode") silently dropped their private repos.

Failure semantics

  • Atomic rebuild. @Transactional wraps the wipe-and-rebuild; any failure (bad token, rate limit) rolls back and the previous graph survives. Verified live against a real rate-limit 403.
  • Per-repo tolerance. Empty repos 404 on language/contributor endpoints; those are caught per iteration and skipped, never aborting the run.
  • Observable errors. A token-free failure summary is stored and surfaced through GET /status (e.g. "GitHub returned 403 — likely the rate limit; add a PAT"), so the UI never reports false success.
  • Single flight. An AtomicBoolean guard makes concurrent refreshes a 409, not a race.

6Frontend

A single static file (src/main/resources/static/index.html) served by the app itself. D3 v7 from a CDN is the only external asset. Three views behind a segmented switcher with #hash deep links:

  • Graph — force-directed layout. Node identity is triple-encoded (color + shape + direct label) so it survives colorblindness and grayscale; the 4-slot categorical palette is validated for CVD separation and contrast in both light and dark themes. Edge width maps to weight, normalized per edge type so byte counts don't visually crush commit counts. Drag, zoom, hover tooltips, click-to-focus neighborhood dimming.
  • Stats — stat tiles plus two horizontal bar charts: languages by share of code (top 12, remainder folded into "Other") and top collaborators. Charts are plain HTML/CSS; each carries a one-line note stating how its numbers are computed.
  • Table — raw nodes and edges, the accessibility fallback and debugging view.

Refresh UX

Username input (persisted in localStorage) and a password-type PAT input (deliberately never persisted). The refresh button POSTs both, polls /status, then refetches — showing either a timestamped success or the stored failure reason.

SVG export

buildExportSvg() clones the live SVG and makes it self-contained: every var(--…) resolved to concrete color values, label fonts and halos inlined as attributes, hover hit-targets stripped, a theme background and legend added, and the viewBox fitted to content. The result renders identically with no page around it — the requirement for embedding in a GitHub profile README. The function is a global on purpose, so a future CI job can call it through a headless browser.

7Key decisions

Relational tables over a graph database

Neo4j-class tooling buys traversal performance the dataset never needs. Two tables keep ops at zero and the query surface obvious. Revisit only if multi-hop queries become a feature.

Full rebuild per refresh, in one transaction

Incremental sync means diffing GitHub state against stored state — a large correctness surface for no user-visible gain at this scale. A transactional rebuild is trivially correct and failure-safe. Cost: node IDs change per refresh; accepted, keys are stable.

Polling over webhooks

Webhooks need a public endpoint — impractical for a localhost personal tool. On-demand refresh matches actual usage (look at your graph occasionally). Deliberately deferred, not rejected.

Bytes as the WRITTEN_IN weight

The original plan stored per-repo fractions; fractions can't aggregate across repos without repo sizes, which made "most-used language" dishonest. Absolute bytes make every percentage derivable and truthful. One-time semantics change; refresh migrates the data.

Per-request credentials with env fallback

Started as server-only env vars; moved to request-scoped so the UI can switch subjects and tokens without restarting. Env vars remain as defaults for headless use. The token never persists anywhere.

Same-origin static frontend

Serving the page from Spring Boot removes CORS, a build pipeline, and a second deploy target. One file, no framework. Right until the frontend grows real state.

8Security & privacy

  • Token handling. The PAT travels once in a request body to the user's own backend, lives in memory for the duration of a single ingestion run, and is never persisted, logged, or echoed. Error summaries are constructed to be token-free.
  • Browser storage. Username is remembered in localStorage for convenience; the token field intentionally is not.
  • Private data in exports. A token-mode graph contains private repo names. The documented flow for public artifacts (README exports) is: refresh in username-only mode first, then export.
  • Deployment boundary. The design assumes localhost. Exposing the backend publicly would require HTTPS and auth in front before the token input is safe to use.

9Operational notes

  • Storage. H2 in file mode at ./data/devidentity.mv.db, survives restarts. AUTO_SERVER=TRUE lets a second process (H2 shell, console) connect while the app runs, ending a recurring class of file-lock failures.
  • Tests. The test profile overrides the datasource to in-memory H2, so builds pass regardless of whether the app is running — and tests can never mutate real ingested data.
  • Rate limits. Ingestion costs roughly 2 + 2·repos API calls. Unauthenticated (60/hr) supports ~25 repos per hour; a token (5000/hr) makes the budget a non-issue. A 403 mid-run rolls back cleanly and reports itself via /status.
  • Verification practice. Every layer was exercised against the live GitHub API (octocat as the public fixture) and the UI screenshot-verified headlessly in both themes.
